# gmsh is deliberately NOT a pip package here. The spack gmsh (docker/spack/spack.yaml,
# built +shared) already produces the Python SDK — lib/gmsh.py + libgmsh.so via the CMake
# option ENABLE_BUILD_DYNAMIC, which +shared turns on (it is NOT gated on a `+python`
# variant, which gmsh has none of — the source of the earlier "no python API" misread). The
# entrypoint's activate.sh puts /opt/views/view/lib on PYTHONPATH, so HEAT's in-process
# `import gmsh` (engineClass -> elmerClass) resolves to the spack copy on BOTH arches
# (verified through /entrypoint.sh on x86_64 and aarch64). A pip gmsh would only shadow the
# view copy — and it ships NO linux-aarch64 wheel — so dropping it removes the sole aarch64
# blocker for free. NB: verify view-provided imports THROUGH /entrypoint.sh; a raw
# `--entrypoint "" python3 -c "import gmsh"` fails because it lacks activate.sh's PYTHONPATH.
scikit-image
scikit-learn
# open3d >=0.19 ships no linux-aarch64 wheel; on arm pip resolves to 0.18.0 (the
# last with one), so the two arches get DIFFERENT versions of a ray-tracing
# dependency unless this is pinned. Left floating for x86 legacy parity — pin
# ==0.18.0 instead if cross-arch reproducibility matters more.
open3d
mitsuba
skorch
# usd-core has never published a linux-aarch64 wheel (wheel-only project), so it
# is x86-only. Safe to skip on arm: ioClass wraps the meshOpsClass import in
# try/except — USD/GLTF export becomes unavailable, everything else runs.
usd-core ; platform_machine == "x86_64"
